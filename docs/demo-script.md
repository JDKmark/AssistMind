## 一、演示准备（提前 10 分钟）

### 1. 环境启动（PowerShell，仓库根目录）

```powershell
# 依赖服务（PostgreSQL/Qdrant/Redis 等，约 40s）
docker-compose up -d

# 后端初始化（backend/ 目录）
cd backend
venv\Scripts\python.exe scripts/init_db.py          # 建表 + 初始用户
venv\Scripts\python.exe scripts/seed_mall_db.py     # 电商业务数据落 PG（real 模式用，幂等）
venv\Scripts\python.exe scripts/seed_mall_kb.py --reset   # 电商知识库
venv\Scripts\python.exe scripts/seed_ops_kb.py --reset    # 运维知识库

# 启动前后端（两个终端）
venv\Scripts\python.exe -m uvicorn app.main:app --port 8001
cd ..\frontend; npm run dev
```

### 2. 演示数据清单（背熟，现场直接念）

| 类型 | 数据 |
|---|---|
| 订单 | `20240801001`（已发货，顺丰 SF1234567890）、`20240801002`（待发货）、`20240801003`（已完成）、`20240801004`（**待付款**，可演示退款被拒） |
| 商品 | `P001` 华为 Mate 60 Pro ¥6999、`P003` 戴森 V12 ¥4990（**无忧退货/快速退款/免费包邮**）、`P005` 联想拯救者 ¥8999 |

### 3. 开场白（30 秒定位）

> 这是 AssistMind——一个 RAG + Agent 的电商智能客服系统。核心不是"能答多少文档问题"，而是**把"答"和"办"连成闭环**：用户咨询走 RAG 检索回答，订单/物流/售后这类需要动手的业务走 Agent 工具调用真实完成，全程 SSE 流式可视化。

## 二、五段演示剧本

### 演示 ① FAQ 知识问答（约 1 分钟）—— 展示 RAG 链路

**输入**：`华为 Mate 60 Pro 多少钱`

**预期画面**：聊天框出现「正在检索知识库」→「查询已改写」→ 回答 + 知识来源列表（演示商品与订单数据.md）

**讲解点**：
- 意图路由先判为 faq → 走 RAG 检索（不是"生成时把整个知识库塞给 LLM"）
- Multi-Query 把问题改写成 3 个变体提升召回，前端有「查询已改写」可视化
- 回答下方列出**知识来源**——这也是 RAG 和裸 LLM 的关键区别：可溯源

**备用问题**：`P003 支持快速退款吗`（服务承诺类，走 query_product 工具或知识库路径）

---

### 演示 ② 订单查询 + 多轮物流（约 2 分钟）—— 展示 Agent 工具调用 + 实体回溯

**输入 1**：`查一下订单 20240801001`

**预期画面**：tool_call / tool_result 事件逐条出现 → 「调用 查询订单」→ **订单卡片**（订单号/状态/实付/物流单号/商品明细）

**输入 2（关键！多轮）**：`物流到哪了`

**预期画面**：不重复提单号，Agent 自动从上一轮提取订单号 → 调用 查询物流 → **物流轨迹卡片**（时间线：已揽收 → 运输中）

**讲解点（这是全场的架构亮点）**：
- Agent 不是"LLM 背数据"——订单/物流是**实时业务数据**，必须调工具，工具返回前禁止编造
- 多轮上下文由**实体识别**保证：规则层抽出订单号（`(?<!\d)20\d{9}(?!\d)`，中文数字边界防手机号误匹配），当前轮没提单号就从历史回溯，自动补填工具参数
- 前端工具调用逐步可视化——**Agent 不是黑盒**

**配套实测（面试提这个非常加分）**：实体识别 on/off 对照实验（`run_eval_agent.py --entity-fill both`）：
- 成功率 on 9/9 = off 9/9（DeepSeek 多轮能力强，成功率持平）
- 效率差异可复现：off 模式多轮物流会**重复调用 query_logistics 2 次**（两次运行均复现），on 模式实体回溯 1 次到位——实体识别省 token、省时延，弱模型下收益更大

### 演示 ③ 退货闭环（约 3 分钟）—— 展示完整 Agent 闭环

**输入 1**：`我要退货`

**预期画面**：Agent 不直接退款——输出 CLARIFY 澄清，追问订单号（参数缺失触发澄清协议）

**输入 2**：`订单号是 20240801003，原因是不想要了`

**预期画面**：先调「查询订单」确认状态（已完成，可售后）→ 再调「申请退款」→ **售后结果卡片**（售后单号 AF20240801003 / 处理中）→ 回答 + 已创建售后工单提示

**讲解点**：
- 这是"**办**"的闭环：校验状态 → 创建售后单（数据源状态机：待付款拒绝 / 可售后状态放行 / 重复申请幂等返回同一单号）→ 沉淀工单，每一步前端可见
- 退款流程的顺序约束写死在 system prompt：先 query_order 确认，再 apply_refund，reason 缺失先问
- 数据层：`MALL_DATA_SOURCE=real` 时售后单落 PostgreSQL，order_sn 唯一约束保证**跨进程幂等**（内存 mock 只在单进程内幂等）

**备用**：`退掉 20240801004`（待付款 → 查单确认后如实告知不可退，同样展示状态机）

### 演示 ④ 运维诊断（扩展能力，约 2 分钟）—— 展示底座能力复用

**输入**：`下单失败了，帮我诊断`

**预期画面**：意图路由识别为 diagnose → 阶段标签流（规划 → 采集证据 → 分析根因）→ 根因报告 + 置信度 + 证据清单（含 degraded 标注）→ 自动创建故障工单

**讲解点**：
- 这不是独立功能，是**复用 RAG + Agent + MCP + 可观测底座**的延伸：Supervisor Agent 并行采集指标/日志/变更/告警/知识库 + 关联相似历史工单
- 数据源 mock/real 双实现 + auto 健康探测降级——和电商数据源同一套门面模式

## 三、四类面试问题话术

### Q1 要不要做 / 为什么值得做（价值判断）

**话术**：
> 客服场景高频问题分两类：**知识咨询**（商品/政策，能"答"）和**业务办理**（查订单/查物流/申请退款，要"办"）。纯 RAG 只能答——它没有数据源，也不知道用户订单状态。所以我在 RAG 之上加了一层 Agent + 工具调用：Agent 通过 MCP 调真实业务工具，把"答"和"办"连成闭环。判断标准是**闭环价值**：这个问题答完之后用户还要不要人工介入？订单查询和售后申请是高频且可自动化的，值得做。

**对照**：ToolAgent（`app/agents/tool_agent.py`）+ 4 个电商业务工具（MCP server）+ 工单沉淀。

### Q2 怎么做（架构设计）

**话术**（按五层讲，每层一句话 + 一个工程细节）：
> 1. **RAG 检索**：混合召回（Qdrant 向量 + BM25 词粒度），RRF 融合 + Reranker 精排 + CRAG 评估；结构感知切块解决长文档和 SQL 召回——代码块整体保留、表格不拆行、DDL 按 CREATE TABLE 切块。
> 2. **查询理解**：三级意图路由（规则→语义→LLM 兜底）外置配置文件热加载；实体识别规则层确定性提取订单号/商品 ID，参数缺失走 CLARIFY 澄清，不编造。
> 3. **Agent 编排**：LangGraph ReAct + Retrieval Before Agency（先检索再决策）；MCP 双向架构——Agent 不直接调本地函数，走 MCP Client → Server，工具实现与 Agent 解耦，加工具不用改 Agent。
> 4. **可靠性**：全链路失败降级表（LLM 重试→切 Ollama→模板兜底；Qdrant 失败仅 BM25；数据源 auto 探测降级 mock）；语义缓存版本号 O(1) 失效。
> 5. **可观测**：Langfuse 单点埋点（LLM 每次调用一个 span），Agent 编排级 trace。

### Q3 怎么迭代（复盘与演进）

**话术**（四个真实迭代案例，面试最加分）：
> 1. **检索质量**：早期单字切分 BM25 无区分度，改成 jieba 词粒度后相关文档得分显著高于无关（区分度从 0 到 0.575，有专项测试 `test_bm25_tokenize.py` 守卫）。
> 2. **生成质量**：answer_relevancy 低分做了三层归因——评分工具链单点退化（Instructor LLM 不支持 n>1 → 换 ragas collections 版 3 问题均值采样）、运维枚举问答天然偏低（指标语义特性，不作为闸门）、prompt 约束（仅基于检索结果回答，不确定宁可不写）。修工具链 + prompt 后 DeepSeek 下 answer_relevancy 从 ~0.53 → **0.703**、faithfulness **0.955**。
> 3. **检索召回优化（用数据定位根因）**：评估发现一批 context_recall=0 样本，逐条对账发现三类根因——① 重排候选太小（RERANK_TOP_K=8 把排名 9-20 的正确文档挡在重排之外）；② SQL DDL 词面与自然语言查询的词汇鸿沟（`CREATE TABLE oms_order` 无法被「订单表是做什么的」命中）；③ YAML 配置语义弱。对应修复：重排候选扩到 20（且**修复重排后未截断的 bug**——候选扩大后必须截回 top-8 上下文，否则噪声淹没生成）、BM25 索引注入 title/section_title/table_comment 词项、SQL chunk 把表级注释拼进检索文本（`【订单表】CREATE TABLE...`）后重灌。效果：oms_order 主表从 top-20 外 → 检索第 3 名，常规样本 faithfulness 0.955→**0.972**、context_precision 0.858→**0.877**、context_recall 0.809→**0.824**。**教训：先逐条对账失败样本再动手，一次改动同时验证检索链路与生成链路的耦合。**
> 4. **切块完整性（孤儿标题 chunk）**：继续逐条对账 recall<0.7 样本，发现全库 51 个「孤儿标题 chunk」——`chunk_text` 把「标题+紧跟表格/fence」拆成两块，标题成为空壳（`## 2. 订单状态流转` 单独成块），浪费 top-8 槽位且表格脱离语义；另有「标题+超长段落」被 `_chunk_plain_text` 切碎。修复：标题行并入结构块（pending 机制）、表格块带 `## {section_title}` 前缀。效果：孤儿 51→0（chunk 254→204），「订单状态 0-5」「oms_order 字段」「ES cluster-name」三个样本 recall 全部 0/0.5→**1.0**，context_recall 0.824→**0.851**、faithfulness 0.972→0.968（持平）。**教训：评估的极端值（recall 0↔1）要结合检索上下文判断是修复生效还是评分方差——华为价格条三跑三值（0.5/1.0/0.0）而检索结果始终正确，属 RAGAS 采样方差。**
> 4. **多轮闭环断裂**：发现前端已发 history 但 task 意图后端丢弃（`chat.py` 只传 query）——「查订单 → 物流到哪了」被当独立问题。修复 API 层传递 + 记忆窗口裁剪，配合实体回溯，多轮链路端到端跑通。**教训：链路闭环要端到端验证，不能只测单点。**

### Q4 怎么验证价值（评估体系）

**话术**：
> 三层验证：① **检索与生成质量**：RAGAS 4 指标，**65 条双数据集**（25 条运维 + 40 条电商，9 条对抗样本单独统计），DeepSeek 下常规样本——电商集 faithfulness 0.968 / context_precision 0.856 / context_recall 0.851 / answer_relevancy 0.682，运维集 faithfulness 0.949 / context_recall 0.976 / answer_relevancy 0.612；② **Agent 闭环**：9 个多轮客服任务端到端 **9/9（100%）**，断言工具链 + 回答 + 参数；③ **功能对照**：实体识别 on/off 对比实验证明确定性收益（成功率持平，但消除重复工具调用）。
>
> 评估基建本身也迭代过：早期断言过严（agent 答"未查询到"被判失败，因为断言只认"不存在"）——**先修评估再信评估**，这是评估可信度的关键。

## 环境（必须遵守，否则数据全废）

- 后端启动**必须**带 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`：模型已本地缓存（`~/.cache/huggingface/hub`），不禁用会走系统代理下载被 502，导致**每次请求重试加载模型（单请求 ~60s）**。
- 基础设施：Qdrant `localhost:6333`、Redis `localhost:16379`（注意不是 6379）、PostgreSQL `localhost:5432`。
- 压测客户端已默认 `trust_env=False`（本机常驻代理会劫持 localhost 请求）。
- 缓存 O(1) 失效（让请求真正走到检索层）：`docker exec smart-cs-redis redis-cli INCR assistmind:kb:version`
- 端口：用户已有实例在 `8002`，**不要占用**；本次用 `8012/8013/8014`。
- 单机压测（Locust 与被测同机，12 核），Locust 单进程即可，报告中需声明该测量偏差。

## 步骤 1 · 429 限流验证

以低限流实例起服务（20 req/min）：

```bash
cd backend
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 LLM_PROVIDER=mock RERANKER_ENABLED=false \
LANGFUSE_PUBLIC_KEY= LANGFUSE_SECRET_KEY= MCP_SERVER_URL=http://localhost:8014/mcp/ \
RATE_LIMIT_PER_MINUTE=20 METRICS_ENABLED=true \
./venv/Scripts/python.exe -m uvicorn app.main:app --port 8014
```

S1 是缓存命中（单请求 ~50ms），10 并发足以在 30s 内超过 20 req/min：

```bash
cd backend/tests/load
LOAD_HOST=http://localhost:8014 LOAD_SCENARIO=s1 LOAD_CSV_DIR=results \
../../venv/Scripts/python.exe -m locust -f locustfile.py --headless -u 10 -r 10 -t 30s \
  --only-summary --csv results/s6_ratelimit
```

取证：
- `curl -s localhost:8014/metrics | grep rate_limited_total` → 期望 `scope="ip"` > 0
- `results/s6_ratelimit_stats.csv` 与明细 CSV 中 429 占比
- 断言 `/metrics` 与 `/api/v1/health` 在限流跳过名单内，**不应**被 429

## 步骤 2 · 故障恢复证据（必须重跑）

> 前序最后一次「恢复轮」被中断，`results/s5_recovery_console.log` 为 **0 字节**，恢复证据缺失，必须重采。

用覆盖文件热切换故障（同一进程不重启）：

```bash
mkdir -p backend/tests/load/results
echo '{"FAULT_RERANKER":"ok","FAULT_QDRANT":"ok","FAULT_LLM":"ok"}' > backend/tests/load/results/faults.json

cd backend
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 LLM_PROVIDER=mock RERANKER_ENABLED=true \
RERANKER_PROVIDER=siliconflow FAULT_OVERRIDE_FILE=<仓库绝对路径>/backend/tests/load/results/faults.json \
LANGFUSE_PUBLIC_KEY= LANGFUSE_SECRET_KEY= MCP_SERVER_URL=http://localhost:8013/mcp/ \
RATE_LIMIT_PER_MINUTE=100000 METRICS_ENABLED=true \
./venv/Scripts/python.exe -m uvicorn app.main:app --port 8013
```

按顺序改写 `faults.json` 并各跑一轮（每轮前先 `INCR assistmind:kb:version` 清缓存，否则走不到检索层）：

| 轮次 | faults.json | 场景命令 |
|---|---|---|
| reranker fail | `{"FAULT_RERANKER":"fail"}` | `LOAD_HOST=http://localhost:8013 LOAD_SCENARIO=s5 LOAD_CSV_DIR=results ../../venv/Scripts/python.exe -m locust -f locustfile.py --headless -u 6 -r 6 -t 40s --only-summary --csv results/s5_fault_reranker` |
| qdrant down | `{"FAULT_QDRANT":"down"}` | 同上，`--csv results/s5_fault_qdrant` |
| llm error | `{"FAULT_LLM":"error"}` | 同上，`--csv results/s5_fault_llm` |
| 恢复对照 | 三个都 `"ok"` | 同上，`--csv results/s5_recovery` |

取证（spec 3.6 要求四件事都给证据）：每轮前后 `curl -s localhost:8013/metrics | grep degradation_total` 快照；
期望值（前序已实测，作为对照）：`reranker/fault_fail=6`、`qdrant/fault_down=24`、`llm/fault_error=20` 且伴随
`llm/fallback=2`、`query_rewrite/fallback=2`；**恢复轮 `degradation_total` 不再增长**即为「无需重启自动恢复」的证据；
后端日志需可见 `[Fault] FAULT_* …` 的 warning 行。

   → **瓶颈在单进程 CPU（本机 embedding 推理与 Python 层开销），而非并发槽/连接池**（T1/T2 未做，待 P3 验证）。

7. **与 spec 的偏差说明**：每阶 180s（满足「≥3 分钟」）、spawn_rate 5/s、400 并发阶的 QPS「回升」是快速失败造成的假象。

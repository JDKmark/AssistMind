## 计划：订单查询增强 — A. PostgreSQL 数据落地 + B. 实体识别关系

### 目标
- **A**：订单/物流/商品/售后数据从内存 mock 迁到 PostgreSQL，MCP 业务工具后端透明切换（契约不变），支持 `MALL_DATA_SOURCE=mock/real/auto`
- **B**：规则+LLM 实体抽取（订单号/商品 ID），建立「实体 → 工具参数补填 → 多轮上下文注入」关系，减少 LLM 编造与 CLARIFY 次数

消费方（MCP Server 4 工具 / ToolAgent / 前端 SSE）零改动——门面与实体层都在现有架构内扩展。

---

### A. PostgreSQL 数据落地

**1. 模型 `backend/app/models/mall.py`（新建）**，仿 ticket.py 风格，继承 `app.models.user.Base`：
- `MallProduct`（mall_products）：id(PK, P001)/name/spec/price(Numeric)/stock/services(JSON 中文列表)
- `MallOrder`（mall_orders）：order_sn(PK)/status(中文枚举)/pay_amount(Numeric)/logistics_no(nullable)/created_at(DateTime)
- `MallOrderItem`（mall_order_items）：id(PK auto)/order_sn(FK)/product_id/name/spec/price/quantity
- `MallLogistics`（mall_logistics）：id(PK auto)/order_sn(FK)/ts/content
- `MallRefund`（mall_refunds）：refund_id(PK, AF{order_sn})/order_sn(FK unique)/reason/status/created_at
- 中文 status 字面值必须与 base.py 契约一致（待付款/待发货/已发货/已完成；售后处理中）

**2. `backend/app/core/mall/real_source.py`（新建）`RealMallDataSource(MallDataSource)`**：
- query_order：查 orders + items 两次查询组装契约 dict；未命中返回 None
- query_logistics：按 ts 正序；未发货/未知返回 []
- query_product：未命中返回 None
- apply_refund：事务内「查订单 → 状态机校验（同 mock：未知/待付款拒绝）→ 查重幂等 → insert」；PG 失败 logger.warning + 返回降级失败 dict，不抛异常
- 会话：`async with async_session() as session`（仿 ticket_service.py 模式）

**3. 门面改造 `backend/app/core/mall/data_source.py`**（参照 ops 门面）：
- `_resolve_source` 按 `MALL_DATA_SOURCE` 切换：mock 恒 mock；real 恒 real；auto=配置了 DATABASE_URL 且 `SELECT 1` 健康探测通过 → real，否则 mock + logger.warning
- 新增 `get_source_mode()`（供前端/日志展示），保留 `reset_source()`

**4. 配置 `backend/app/config.py`**：新增 `MALL_DATA_SOURCE: str = "mock"`（默认 mock，测试与演示行为不变；.env 可切 real/auto）

**5. Seed `backend/scripts/seed_mall_db.py`（新建）**：
- 从 `app.core.mall.mock_source` import PRODUCTS/ORDERS/LOGISTICS 常量作为**单一数据来源**（保证 mock 与 real 数据永远一致）
- 幂等：表非空跳过
- `scripts/init_db.py` 加一行 noqa import 注册 mall 模型到 metadata（create_all 建表）

**6. 测试**：
- `tests/unit/test_mall_data_source.py` 扩展：门面切换逻辑（mock 恒 mock；real 分支 patch real_source 构造；auto 探测失败降级 mock）
- `tests/integration/test_mall_pg.py`（标记 integration，需 Docker PG）：seed → real_source 四接口读写 + 退款幂等 + 契约形状
- 现有 test_mall_data_source / test_mcp_mall_tools / test_tool_agent 保持全绿（默认 mock，不受影响）

### B. 实体识别关系

**1. `backend/app/core/mall/entity_extractor.py`（新建）**：
- 规则层（确定性优先，零 LLM 成本）：订单号 `\b20\d{9}\b`（11 位、20 开头，匹配演示单号 20240801001，避免误匹配手机号）；商品 ID `\bP\d{3}\b`
- 关系映射 `ENTITY_TO_TOOLS`：order_sn → [query_order, query_logistics, apply_refund]；product_id → [query_product]
- `extract(query, history=None) -> {order_sn, product_id}`：history 合并（多轮「物流到哪了」场景从历史提单号）
- 规则未命中时可选 LLM 兜底（结构化输出抽取实体，失败降级返回空 dict + warning，不阻塞）

**2. ToolAgent 集成 `backend/app/agents/tool_agent.py`**：
- `execute_tool` 拦截补填：工具在 ENTITY_TO_TOOLS 映射内且 input 缺关键参数（order_sn/product_id）时，用实体抽取结果补填，日志记录 `[ToolAgent] 实体补填`
- `think` 前置：抽取到实体时向 messages 注入 `AIMessage(content="（实体识别：已提取订单号 xxx）")`，帮助 LLM 多轮对话正确选参
- prompt 追加一句「系统可能已自动提取实体并补填参数，以补填结果为准」

**3. 测试 `tests/unit/test_entity_extractor.py`（新建）**：
- 规则抽取：订单号/商品 ID/无实体/多轮历史提取/手机号不误匹配
- ToolAgent 补填：LLM 输出 Action 但参数缺失 → 补填后调用（mock MCP 断言 call_tool 参数）；无实体时不补填保持原行为

### 风险与降级
- PG 不可达：auto 模式自动降级 mock（logger.warning），与 ops 门面一致；real 模式单源失败返回降级值不抛异常
- 实体正则误匹配：订单号模式限定 `20\d{9}` 且优先在 task 意图语境使用；LLM 兜底失败静默降级
- 默认 MALL_DATA_SOURCE=mock，无 Docker 环境一切测试/演示照旧

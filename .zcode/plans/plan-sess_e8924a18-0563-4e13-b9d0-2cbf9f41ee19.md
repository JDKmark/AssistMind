## 计划：phase8 多轮对话槽位状态机（轻量版）

### 背景
多轮对话状态管理只做了一半：history 传递 + 上下文三函数 + 实体回溯（order_sn/product_id）已就位；但**槽位状态机缺失**——「退货需 order_sn + reason」的收集完全靠 LLM 从 history 猜 + CLARIFY 追问，无「还缺哪个槽位」的确定性判断（reason/title/description 无规则提取）。

### 改动（Lite：单模块 + 集成 + 测试，不动前端/API 契约）
1. **`core/dialog/state.py` 新增**（纯函数，无 session 存储）：
   - `extract_slots(query, history) -> dict`：复用 entity_extractor 规则（order_sn/product_id 含历史回溯）+ 新增 reason（关键词「原因/因为/不想要/质量问题/七天无理由/重复购买」等）/ title / description 规则提取
   - `required_slots(intent) -> list`：refund=[order_sn, reason]、logistics=[order_sn]、order=[order_sn]、ticket=[title, description]
   - `missing_slots(intent, slots) -> list`：缺失判断
2. **ToolAgent 集成**：think 实体提示注入时顺带注入缺失槽位提示（如「还缺退款原因」），不重复索要已有槽位
3. **测试**：`test_dialog_state.py`（提取/映射/缺失判断）+ `test_tool_agent.py` 补用例

### 验证
- 单测全绿（332 → 新增）
- `run_eval_agent.py` 退货流程保持通过（理想：多轮任务追问轮次减少）

### 风险
- 纯函数无状态，不引入 session/Redis，行为向后兼容；CLARIFY 机制保留（LLM 仍可追问，但有了确定性判断辅助）
